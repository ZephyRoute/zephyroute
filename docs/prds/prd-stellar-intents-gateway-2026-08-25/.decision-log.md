- **2026-09-22** — Completed Story 1.10 (Sign and Submit Within the Authorization Window), Issue #5. The countdown's expiry timestamp is derived from real data at two layers, never a guess from architecture.md's documented 12-60 ledger range: `src/lib/deposit-xdr-inspector.ts` parses the already-built, already-validated deposit XDR with `@stellar/stellar-sdk`'s `TransactionBuilder.fromXDR` and reads the real `signatureExpirationLedger` off its Soroban authorization entry via the SDK's own `inspectAuthEntry` helper (a genuinely useful, previously-unused piece of the SDK's public API, found by reading its `.d.ts` rather than hand-decoding the XDR structure); `getLedgerTiming()` (new, in `horizon.ts`) projects that ledger to a wall-clock timestamp using the network's actual observed close interval between its two most recent ledgers, not a hardcoded assumption. The hook (`useDepositSigning.ts`) ticks the countdown locally between 20-second resyncs, and an actually-expired window (detected during a resync, not just a client-side timer hitting zero) triggers an automatic rebuild via the same `/api/deposit/build` route, surfaced through an always-rendered `aria-live="polite"` region in `DepositSigningPanel.tsx` per AC #2. "Minimum guaranteed balance" is computed directly from the same `slippageBps` passed into the build call (`amount * (10000 - slippageBps) / 10000`, using `BigInt` throughout, since DeFindex computes `amounts_min` server-side from that value and doesn't return the derived number in its response) rather than attempting to decode it back out of the XDR's contract-call arguments, which would need DeFindex's specific vault ABI, not available from any source this project could verify. A wallet disconnect mid-signature is detected by racing the kit's own `DISCONNECT` event against the signing promise in `wallet-kit.ts`'s new `signDepositTransaction()`, distinguished from an ordinary cancel via a `reason: 'disconnected' | 'cancelled'` field on `DepositSigningError` rather than string-matching the message, so a disconnect always renders its own explicit reconnect state (AC #3) and is never submitted or assumed successful. The insufficient-XLM-for-fee check reads the exact fee already encoded in the built transaction (`parsed.fee` off the same parsed XDR, real data DeFindex's own simulation already committed to, not a separate guess) and compares it against the depositor's real Horizon balance before the signature prompt ever renders (AC #4). `buildDepositTransaction()` (Story 1.9) and its route now also return `vaultAddress`, since the UI needs to display the real destination for review-before-signing but can no longer read `DEFINDEX_VAULT_ADDRESS` itself now that it's correctly server-only (Issue #3).
